# 브랜업 신입직원 온보딩 및 공통업무 매뉴얼

> 이 문서는 브랜업에 새로 합류한 직원이 회사의 정체성, 기본 업무 도구, 공통 업무 흐름 및 담당 직무를 빠르게 이해하고 독립적으로 업무를 수행할 수 있도록 돕기 위한 사내 표준 매뉴얼입니다.

## 0. 문서 사용 안내

- 신입직원은 입사 첫날부터 본 문서를 순서대로 확인합니다.
- 각 항목의 체크박스는 실제 완료 후 표시합니다.
- `[입력 필요]` 표시는 회사 담당자가 실제 정보로 보완해야 하는 항목입니다.
- 비밀번호, 주민등록번호, 계좌번호, 고객 개인정보, API 키 등 민감정보는 이 문서나 사내 LLM에 입력하지 않습니다.
- 내용이 실제 업무와 다르면 임의로 따르지 말고 담당자에게 확인한 후 문서 수정 요청을 남깁니다.

### 주요 문의처

| 구분 | 담당자/부서 | 연락 방법 |
|---|---|---|
| 온보딩 총괄 | 이향석 | `[입력 필요: Slack 사용자명 또는 문의 채널]` |
| 사내 메일·Slack·대시보드 계정 | 이향석 | `[입력 필요: Slack 사용자명 또는 문의 채널]` |
| 인사·근태·복리후생 | 이향석 | `[입력 필요: Slack 사용자명 또는 문의 채널]` |
| 정보보안·개인정보 | 이향석 | `[입력 필요: 긴급 신고 채널 또는 연락처]` |
| 부서 직무교육 | 소속 부서장 또는 지정 멘토 | Slack DM 또는 지정 채널 |

# 1. 브랜업의 정체성

## 1.1 회사 기본 정보

| 항목 | 내용 |
|---|---|
| 회사명 | 주식회사 브랜업 |
| 설립 목적 | `[입력 필요]` |
| 미션 | `[입력 필요: 브랜업이 고객과 사회를 위해 존재하는 이유]` |
| 비전 | `[입력 필요: 중장기적으로 만들고자 하는 모습]` |
| 핵심 제품·서비스 | `[입력 필요]` |
| 주요 고객 | 에나지크, 정육공방 |
| 핵심 가치 | `[입력 필요: 예—고객 중심, 실행, 책임, 협업, 학습]` |
| 조직도 | `[사내 조직도 링크 입력 필요]` |

## 1.2 브랜업의 기본 업무 원칙

1. 고객과 회사에 미치는 영향을 기준으로 우선순위를 정합니다.
2. 업무는 담당자, 목적, 기한, 산출물이 명확해야 합니다.
3. 구두로 결정한 중요한 내용은 대시보드 또는 Slack에 기록합니다.
4. 문제가 예상되면 마감 직전이 아니라 발견 즉시 공유합니다.
5. 사실, 의견, 추측을 구분해 보고합니다.
6. 개인정보와 회사 기밀을 필요한 범위에서만 열람·공유합니다.
7. 반복되는 업무는 문서화하고 개선합니다.

| 순서 | 계정 | 담당자 | 접속·저장 위치 | 완료 기준 |
|---|---|---|---|---|

| 6 | 사내 LLM 위키 | `[입력 필요: GitHub 저장소 관리자]` | [브랜업 사내 LLM 위키 저장소](https://github.com/howwow25/branup-wiki) | GitHub 조직 초대, 저장소 읽기 권한 및 문서 검색 확인 |
| 7 | 텔레그램 | 이향석 | 브랜업 업무용 텔레그램 | 신입직원 ID 전달, 연락처 등록 및 업무 채널 참여 확인 |
| 8 | 승인된 AI 서비스 | 이향석 | `[사용할 AI 서비스와 접속 주소 입력 필요]` | 계정 또는 사용 방법을 공유받고 보안수칙 확인 |
| 9 | 직무별 서비스 계정 | 소속 부서장 | 직무별 지정 서비스 | 직무 수행에 필요한 최소 권한 확인 |

## 2.2 계정 생성 표준

- 사내 메일 주소 규칙: `id@branup.co.kr`
- 메일 로그인 주소: [메일플러그 로그인](https://login.mailplug.com/auth/login?host_domain=branup.co.kr)
- 표시 이름 규칙: `[입력 필요: 예—홍길동 / 사업운영팀]`
- 초기 비밀번호는 로그인 직후 변경합니다.
- 동일한 비밀번호를 여러 서비스에서 재사용하지 않습니다.
- 가능하면 다중 인증(MFA)을 설정합니다.
- 개인 계정으로 회사 문서나 고객 자료를 공유하지 않습니다.
- 퇴사·휴직·부서 이동 시 담당자는 당일 권한을 회수하거나 변경합니다.

# 3. 브랜업 대시보드 작성 방법

## 3.1 작성 목적

브랜업 대시보드는 업무 현황을 한곳에서 공유하고 담당자, 일정, 진행 상태 및 결과를 추적하기 위한 공식 기록 도구입니다. 대시보드에 기록되지 않은 업무는 누락되거나 협업자가 알기 어렵습니다.

## 3.2 기본 작성 항목

대시보드의 실제 필드명이 다를 경우 아래 의미에 맞는 항목을 사용합니다.

| 항목 | 작성 방법 |
|---|---|
| 업무명 | 동사와 결과 중심으로 구체적으로 작성 |
| 목적/배경 | 왜 해야 하는지 1~3문장으로 작성 |
| 담당자 | 최종 실행 책임자 1명을 명확히 지정 |
| 협업자 | 검토·자료 제공·승인이 필요한 사람 지정 |
| 시작일/마감일 | 실제 수행 가능한 일정 입력 |
| 우선순위 | 긴급도와 중요도를 기준으로 설정 |
| 상태 | 예정 / 진행 중 / 검토 요청 / 보류 / 완료 |
| 진행 내용 | 현재까지 한 일과 다음 행동 기록 |
| 결과물 | 문서, 파일, URL 등 산출물 링크 |
| 이슈/지원 요청 | 막힌 이유, 필요한 결정, 요청 대상 기록 |

### 좋은 업무명 예시

- 나쁨: `자료 조사`
- 좋음: `7월 경쟁사 5곳 가격정책 조사 및 비교표 작성`
- 나쁨: `고객 연락`
- 좋음: `A고객 계약 갱신 조건 확인 및 7월 30일까지 회신`

## 3.3 업무 등록 절차

1. 업무의 목적과 완료 기준을 확인합니다.
2. 유사하거나 중복된 업무가 이미 등록되어 있는지 검색합니다.
3. 업무명, 담당자, 마감일, 우선순위, 완료 기준을 입력합니다.
4. 관련 문서와 Slack 대화 링크를 첨부합니다.
5. 업무 상태가 바뀌면 당일 업데이트합니다.
6. 검토가 필요하면 상태를 `검토 요청`으로 바꾸고 검토자를 태그합니다.
7. 완료 시 결과물 링크와 최종 결과를 기록한 후 `완료` 처리합니다.

## 3.4 진행 상황 작성 형식

```text
[현재 상태]
- 완료한 일:
- 진행 중인 일:
- 다음 행동:
- 예상 완료일:
- 이슈 또는 의사결정 필요사항:
```

## 3.5 완료 기준

단순히 작업을 끝냈다는 이유만으로 완료 처리하지 않습니다.

- 요청된 산출물이 작성되어 있습니다.
- 관련 검토 또는 승인이 완료되었습니다.
- 파일과 링크가 대시보드에 연결되어 있습니다.
- 후속 업무가 있으면 별도 업무로 등록되어 있습니다.
- 협업자가 결과를 찾고 이해할 수 있습니다.

## 3.6 데이터 품질 원칙

- 같은 내용을 중복 등록하지 않습니다.
- 날짜, 수치, 고객명, 파일 버전을 확인합니다.
- 고객 개인정보와 비밀번호는 입력하지 않습니다.
- 담당자가 바뀌면 즉시 수정합니다.
- 보류 업무에는 보류 사유와 재검토 날짜를 적습니다.

# 4. Slack 사용법

## 4.1 기본 원칙

- 공개 가능한 업무 대화는 DM보다 관련 채널에서 진행합니다.
- 질문에는 배경, 확인한 내용, 필요한 답변, 희망 기한을 포함합니다.
- 중요한 결정은 대화로 끝내지 말고 대시보드 또는 공식 문서에 반영합니다.
- 메시지를 읽었다는 의미로 적절한 이모지 반응을 사용할 수 있습니다.
- 긴급하지 않은 업무는 근무시간을 고려해 전달합니다.

## 4.2 프로필 설정

- 이름: `[회사 표준 입력 필요: 예—홍길동]`
- 직책/부서: 실제 소속과 역할
- 프로필 사진: 본인을 식별할 수 있는 이미지
- 상태: 회의, 외근, 휴가, 집중 업무 등
- 시간대: `Asia/Seoul`

## 4.3 권장 채널 체계

실제 채널 이름은 회사 운영 기준에 맞게 수정합니다.

| 채널 예시 | 용도 |
|---|---|
| `#공지` | 전사 공지, 정책 변경 |
| `#전사-소통` | 전사 공유와 일반 소통 |
| `#주간업무` | 주간보고 제출 및 회의 안내 |
| `#부서명` | 부서 업무 협업 |
| `#프로젝트-명` | 프로젝트 단위 협업 |
| `#질문-도움` | 업무 질문과 해결 방법 공유 |

## 4.4 메시지 작성 예시

```text
[검토 요청] 7월 고객 안내문 초안

- 목적: 신규 요금제 적용 전 고객 공지
- 확인 요청: 문구와 적용 일자
- 문서: [링크]
- 회신 희망: 7월 29일 14:00
```

## 4.5 스레드, 멘션, DM

- 특정 메시지에 대한 답변은 스레드로 작성합니다.
- `@이름`은 해당 사람의 확인이나 행동이 필요할 때만 사용합니다.
- `@channel`, `@here`는 다수에게 즉시 알릴 필요가 있을 때 제한적으로 사용합니다.
- 개인 인사, 민감한 상담, 개인별 피드백은 DM을 사용합니다.
- DM에서 결정된 공통 업무 내용은 관련 채널이나 대시보드에 요약합니다.

## 4.6 파일 공유 및 검색

- 파일명에는 내용과 날짜 또는 버전을 포함합니다.
  - 예: `2026-07_고객사별_매출현황_v1.0.xlsx`
- 최종 파일은 지정된 회사 저장소에 보관하고 Slack에는 링크를 공유합니다.
- 같은 파일을 여러 채널에 반복 업로드하지 않습니다.
- 질문 전에 Slack과 사내 LLM 위키에서 관련 내용을 검색합니다.

# 5. AI 기본교육

## 5.1 AI의 올바른 역할

AI는 초안 작성, 요약, 아이디어 발굴, 분류, 표 작성, 반복 업무 개선을 지원하는 도구입니다. AI의 답변은 최종 결론이나 사실을 보장하지 않으므로 담당자가 반드시 검토합니다.

## 5.2 사용할 수 있는 업무 예시

- 이메일, 공지, 보고서의 초안 작성
- 회의 내용 요약 및 할 일 정리
- 문서 맞춤법과 표현 개선
- 아이디어와 체크리스트 생성
- 공개 자료의 비교·분류·요약
- 공식이나 코드의 초안 작성
- 사내 LLM 위키에서 규정과 업무 절차 검색

## 5.3 입력하면 안 되는 정보

승인되지 않은 외부 AI에는 다음 정보를 입력하지 않습니다.

- 주민등록번호, 연락처, 계좌번호 등 개인정보
- 고객 명단, 계약서 원문, 미공개 가격과 매출
- 비밀번호, 인증번호, API 키, 접근 토큰
- 소스코드, 영업비밀, 미공개 사업계획
- 인사평가, 급여, 징계 및 건강정보
- 회사가 별도로 기밀로 지정한 정보

정보 입력 가능 여부가 불확실하면 정보보안 담당자에게 확인합니다.

## 5.4 좋은 프롬프트 작성법

다음 다섯 가지를 포함하면 결과의 품질이 높아집니다.

1. 역할: AI가 어떤 관점에서 답할지
2. 목적: 무엇을 만들거나 해결할지
3. 배경: 필요한 상황과 독자
4. 조건: 분량, 말투, 금지사항, 마감
5. 출력 형식: 표, 목록, 이메일, 보고서 등

```text
당신은 브랜업의 사업운영 담당자입니다.
신규 고객에게 보낼 서비스 시작 안내 이메일 초안을 작성하세요.
독자는 서비스를 처음 사용하는 실무자이며, 친절하고 간결한 말투를 사용하세요.
시작일, 준비사항, 문의 방법을 포함하고 500자 이내로 작성하세요.
사실을 추측하지 말고 확인이 필요한 내용은 [확인 필요]로 표시하세요.
```

## 5.5 AI 결과 검토 체크리스트

- [ ] 사실, 날짜, 수치, 고유명사를 원자료와 대조했다.
- [ ] 존재하지 않는 정책이나 사례를 만들어내지 않았는지 확인했다.
- [ ] 개인정보와 기밀정보가 포함되지 않았다.
- [ ] 저작권과 출처를 확인했다.
- [ ] 차별적이거나 부적절한 표현이 없는지 확인했다.
- [ ] 최종 책임자가 직접 읽고 승인했다.
- [ ] 중요한 의사결정은 공식 근거를 함께 기록했다.

## 5.6 사내 LLM 위키 사용 원칙

- 먼저 구체적인 질문을 하고, 답변의 근거 문서와 최신 수정일을 확인합니다.
- 근거 링크가 없거나 서로 다른 답이 나오면 문서 담당자에게 확인합니다.
- 틀린 답변을 발견하면 원본 문서를 먼저 수정한 후 재학습 또는 재색인을 요청합니다.
- LLM 답변보다 최신 공식 규정, 계약서, 승인된 공지를 우선합니다.

# 13. 자주 묻는 질문

## Q. 업무 요청을 구두로 받았습니다. 어떻게 해야 하나요?

목적, 결과물, 기한을 확인한 뒤 대시보드에 등록합니다. 요청 내용이 불명확하면 실행 전에 요청자와 완료 기준을 합의합니다.

## Q. 대시보드와 Slack 중 어디에 작성해야 하나요?

Slack은 대화와 빠른 협업에 사용하고, 대시보드는 업무 상태와 공식 결과 기록에 사용합니다. 중요한 결정은 대시보드 또는 공식 문서에 남깁니다.

## Q. 마감일을 지키기 어려울 것 같습니다.

문제를 인지한 즉시 현재 상태, 지연 사유, 영향, 대응안과 변경 희망일을 담당자와 부서장에게 공유합니다.

## Q. AI가 작성한 결과물을 그대로 사용해도 되나요?

안 됩니다. 담당자가 사실, 수치, 개인정보, 저작권, 표현을 검토하고 필요한 승인을 받은 후 사용합니다.

## Q. 사내 LLM 답변과 공식 문서가 다릅니다.

최신 공식 문서를 우선합니다. 문서 담당자에게 차이를 알리고 원본 문서와 LLM 색인을 수정합니다.

## Q. 업무 파일을 어디에 저장해야 하나요?

회사가 지정한 Google Drive의 부서 또는 프로젝트 폴더에 원본과 최종본을 저장합니다. 개인 PC나 Slack에만 보관하지 않습니다.

- **Google Drive:** 업무 파일의 원본·작업본·최종본 공식 보관
- **브랜업 대시보드:** 업무 진행 상태, 결과 요약 및 Google Drive 문서 링크 기록
- **Slack:** 업무 대화, 알림 및 문서 링크 공유

# 14. 사내 LLM 위키 등록 및 유지관리 기준

## 14.1 등록 전 점검

- [ ] 문서 책임자(owner)가 지정되어 있다.
- [ ] 최신 수정일과 버전이 표시되어 있다.
- [ ] `[입력 필요]` 항목이 실제 정보로 교체되어 있다.
- [ ] 개인정보, 비밀번호, API 키, 고객 기밀이 없다.
- [ ] 중복 문서가 없거나 대표 문서가 지정되어 있다.
- [ ] 관련 규정과 양식 링크가 유효하다.
- [ ] 폐기 예정 문서와 최신 문서가 구분되어 있다.

## 14.2 LLM 검색 품질을 위한 문서 작성 원칙

- 한 문서에는 하나의 명확한 주제를 중심으로 작성합니다.
- 제목과 소제목에 실제 직원이 검색할 용어를 사용합니다.
- 약어는 처음 등장할 때 전체 이름과 함께 씁니다.
- 일정, 담당자, 예외, 완료 기준을 구체적으로 기록합니다.
- 표와 체크리스트를 활용하되 핵심 의미를 문장으로도 설명합니다.
- 변경 시 버전, 수정일, 변경 내용을 남깁니다.
